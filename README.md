XanosMerks. Версия 1.0.0. Автор CharmLxt (PyPI: CharmLxt, email: reception.mailspypi@gmail.com). Ссылка на GitHub: https://github.com/CharmLxt/XanosMerks.





Это движок для запуска больших языковых моделей (LLM) прямо на своём компьютере, без PyTorch, без CUDA, без видеокарты. Только чистый Python и numpy. Он не пытается быть быстрее, чем llama.cpp или PyTorch — его задача в другом: чтобы вы могли скачать веса модели и запустить её, разобравшись, что происходит внутри, а не махая чёрным ящиком. Каждый шаг можно посмотреть, потрогать руками, заменить на свой. Если вы хотите понять, как устроена генерация текста изнутри — это подходящий инструмент. Если хотите просто быстро получить ответ — берите llama.cpp.





Установка — одна команда: pip install XanosMerks. После неё в системе появятся две консольные утилиты (xanosmerks-gamtype и xanosmerks-meanflare) и сам пакет, который импортируется как xanosmerks. Опционально, если у вас уже стоит CharmPkk, поставьте XanosMerks\[charm] — тогда все таблицы и баннеры в консольных утилитах будут цветными, с рамками и градиентами. Без CharmPkk всё работает так же, просто выглядит скромнее.





Первый запуск выглядит так. Вы качаете папку модели с Hugging Face (там должны быть config.json, tokenizer.json и model.safetensors). Дальше в Python:



&#x20;   from xanosmerks.gamtype import inspect\_model

&#x20;   from xanosmerks.gamtype.support\_tools.sup2\_spr.path\_utils import find\_tokenizer

&#x20;   from xanosmerks.meanflare import load\_model\_weights

&#x20;   from xanosmerks.genof11mo import Generator



&#x20;   passport = inspect\_model("путь/к/модели")

&#x20;   config = passport\["config"]

&#x20;   tokenizer = \_\_import\_\_("xanosmerks.gamtype", fromlist=\["parse\_tokenizer"]).parse\_tokenizer(find\_tokenizer("путь/к/модели"))

&#x20;   weights, \_ = load\_model\_weights("путь/к/модели", dtype="float16")

&#x20;   weights\_f32 = {k: v.astype("float32") for k, v in weights.items()}



&#x20;   generator = Generator(config, weights\_f32, tokenizer)

&#x20;   print(generator.generate("Привет, как дела?", max\_new\_tokens=50))



Это всё. Модель загружена, генерация работает. Дальше — расскажу, что делает каждый модуль и зачем он нужен.





gamtype — это первое, с чего начинается любая работа с моделью. Его задача — открыть папку модели и рассказать, что там внутри, ничего не загружая в память. Он читает config.json, tokenizer.json, проверяет safetensors-файлы и gguf-файлы (если они есть) и собирает «паспорт»: сколько слоёв, сколько голов, какой словарь, какая архитектура (Llama, Mistral, Mixtral, Qwen, Gemma, DeepSeek и ещё десяток), сколько параметров, сколько это займёт памяти в разных dtype, какие есть проблемы в конфиге. Если модель битая — gamtype скажет, что именно не так, ещё до того, как вы потратите гигабайты RAM. Если у вас gguf-модель (например, квантованная Q4\_K\_M) — gamtype её тоже прочитает и покажет, какие тензоры и какой квант. Через CLI это делается командой xanosmerks-gamtype inspect путь/к/модели — вывод в консоль, красиво и с рекомендациями.





meanflare — это загрузчик весов. Он берёт файлы safetensors (одиночные или шардированные), gguf или npy и превращает их в numpy-массивы, которые уже можно скармливать модели. Умеет читать через mmap (быстро и с экономией RAM), умеет деквантовать gguf-тензоры (Q4\_0, Q4\_1, Q5\_0, Q5\_1, Q8\_0, Q8\_1, Q2\_K, Q3\_K, Q4\_K, Q5\_K, Q6\_K, Q8\_K, BF16, F16, F32 — всё, кроме очень редких IQ-квантов и тернарных TQ, для них честный NotImplementedError с понятным сообщением). Если вам не нужны все веса сразу — есть ленивый режим: создаёте TensorHandle на каждый тензор, данные читаются с диска только при первом обращении, а MemoryManager следит за бюджетом RAM и выгружает давно не использованные тензоры по LRU. Это спасает, когда модель весит 30 ГБ, а RAM всего 16. Ещё meanflare умеет конвертировать веса из одного dtype в другой: bf16 → fp32, fp8 → fp16, int8 → fp16 — всё через точные numpy-операции без потери данных сверх самого преобразования. Через CLI: xanosmerks-meanflare inspect (метаданные без загрузки), load (загрузить), convert (план конвертации), lazy (ленивый индекс), stress (стресс-тест LRU).





genof11mo (внутри пакета называется genof11mo, читается как «ген-оф-одиннадцать-плюс-мо») — это сам forward-pass, ядро инференса. Здесь живёт весь трансформер: RMSNorm, LayerNorm, RoPE (с поддержкой linear/dynamic/llama3 scaling), Multi-Head Attention с GQA/MQA (через broadcast без np.repeat — экономия памяти до 8 раз), MLA для DeepSeek V2/V3, SwiGLU, MoE для Mixtral (sort-based dispatch, а не перебор экспертов в цикле), FusedMLP через 9was9. Есть собственный BPE-токенизатор (byte-level, как в GPT-2) с корректной предварительной токенизацией (буквы отдельно от цифр). Генератор умеет всё: temperature, top-k, top-p, min-p, typical sampling, repetition penalty, stop sequences, обрезка слишком длинного промпта (truncate=start/middle/none), batch-генерация с паддингом для промптов разной длины, и всё это работает и с обычным KVCache, и с nsofi40, и с MLA. Для каждой стратегии сэмплинга — отдельная функция, чтобы можно было собрать свой sampler с нуля.





nsofi40 — это менеджер KV-кэша для длинных контекстов. Обычный KVCache из ninewas9 держит всё до max\_seq\_len и падает при переполнении. nsofi40 решает эту проблему через sliding window + attention sink (идея из StreamingLLM): хранит только первые N токенов (sink, обычно 4 — они якорят softmax) и последние W токенов (window), а всё, что между ними, выбрасывает. Модель может генерировать бесконечно, не теряя качества. Реализовано через ring buffer с дублированием (двойной буфер по оси seq), поэтому append — O(1), нет сдвигов памяти. Отдельно хранится absolute\_position (растёт бесконечно) и cur\_len (что модель видит сейчас) — это важно, потому что RoPE новые токены поворачивает на абсолютной позиции, а не на cur\_len. Если модель деградирует при сдвиге окна — включаете eviction=h2o (Heavy Hitters Oracle): хранит не всё окно, а токены с наибольшими накопленными attention scores. Это работает и для обычного внимания, и для MLA. Плюс есть nsofi40.metrics() — оттуда видно, сколько токенов вытеснено, когда заполнился sink, когда окно, реальный и виртуальный размер памяти, коэффициент сжатия. Совместимость полная: get() возвращает \[sink; window] в том же формате, что KVCache.get(), а get\_parts() возвращает четыре отдельных view (sink\_k, sink\_v, window\_k, window\_v) — на них attention считает два matmul вместо одной склейки, без np.concatenate на каждом forward.





msisp — это стабилизатор. Когда модель большая, а RAM мало, Python падает с MemoryError или numpy.\_ArrayMemoryError, и вы теряете всё. msisp перехватывает это: MemoryMonitor читает системную память (Windows, Linux, macOS — без psutil), OOMGuard перед крупными аллокациями проверяет «а влезет ли», при нехватке сначала вызывает зарегистрированные evacuation-функции (например, выгрузить KV-кэш, unload все тензоры meanflare), потом пробует ещё раз, и только если совсем плохо — бросает OOMGuardError или запускает GracefulShutdown. GracefulShutdown — это очередь callback'ов с приоритетами: сначала сохранить чекпоинт, потом выгрузить кэши, потом закрыть файлы, потом flush логов. У каждого callback таймаут, ошибки не роняют всю очередь. install\_default\_handlers() связывает всё вместе: создаёт глобальный реестр, регистрирует эвакуацию всех KV-кэшей и MemoryManager'ов, ставит SIGINT-обработчик. Это последний рубеж перед крашем.





vofcf32 (внутри пакета vofcf32, читается «в-оф-ц-ф-тридцать-два») — это квантизация. Когда модель в float16 всё ещё не влезает в память, можно перевести часть весов в INT8 или FP8 с минимальной потерей качества. Quantizer умеет int8 (per\_tensor, per\_channel, per\_group с group\_size по умолчанию 128, symmetric или asymmetric), fp8 e4m3 и fp8 e5m2. Per-group — это то, что используется в GPTQ и AWQ; при правильном group\_size потери качества почти нулевые. FP8 encode сделан через round-to-nearest-even, как в эталонной реализации, а не через наивный searchsorted. calibrate() проходит по всей модели и подбирает scale/zero\_point для каждого тензора, не квантизуя их (параметры можно сохранить в JSON и загрузить обратно). evaluate\_quality() считает MSE, MAE, cosine similarity, SNR и max error — чтобы понять, стоит ли вообще квантизовать этот слой. quality\_report() агрегирует по всей модели и находит worst tensor. choose\_dtype\_for\_budget() смотрит на текущее потребление и подбирает максимально точный dtype, который влезет в бюджет. convert\_with\_policy() применяет правила («embed → fp16, attention → int8, lm\_head → fp16») и сохраняет параметры квантизации в stats. Это то, чего не хватает в meanflare.convert: тот просто механически конвертирует, а vofcf32 думает.





quacdualc — это оптимизатор графа, operator fusion. Идея простая: если две операции идут подряд и не мешают друг другу, их можно слить в одну и сэкономить на промежуточной аллокации. Например, RMSNorm + Linear: не нужно материализовать нормированный x отдельно, его можно сразу подать в matmul. quacdualc умеет находить такие паттерны в графе и в слоях трансформера. На уровне графа: Graph + Node + Op, apply\_fusions находит все пары и сжимает, analyze показывает, сколько паттернов найдено и какое ожидается ускорение. На уровне слоя: optimize\_transformer\_layer() принимает обычный TransformerLayer из genof11mo и возвращает OptimizedLayer с fused-операциями, но с теми же весами (проверено np.allclose(original(x), optimized(x), atol=1e-5)). Fusion для attention (norm + QKV), для MLP (norm + gate/up + swiglu + down), для residual (add + norm). MoE и MLA пока не фьюзятся — там своя специфика, отдельный шаг. Реальный выигрыш от fusion в numpy — 5-10%, но это выигрыш бесплатно, без потери качества.





collapse7 — это супервизор, который связывает всё вместе. Он регистрирует каждый модуль (gamtype, meanflare, genof11mo, nsofi40, msisp, vofcf32, quacdualc — ровно семь) и знает, как проверить, что модуль жив. У каждого модуля есть health\_check (короткая проверка «ты работаешь?»), diagnose (что именно не так) и fix (что можно сделать автоматически). По расписанию (Collapse7Monitor) или по требованию (check\_all) супервизор проходит по всем и собирает статусы. Если модуль упал — handle\_failure запускает цепочку: freeze всех зависимых модулей (пока модуль не починится, никто от него не зависит), diagnose, fix, unfreeze. Если fix провалился max\_retries раз подряд — вызывает msisp.GracefulShutdown, чтобы корректно всё завершить. Freeze теперь жёсткий: если вы оборачиваете функцию в @supervisor.protected("nsofi40") или в with supervisor.guard("nsofi40"), при попытке вызова замороженного модуля будет Collapse7FrozenError. Это не мягкое пожелание, а реальная защита. Регистрируется всё одной строкой: register\_defaults(Collapse7()).





charm\_enhance — это тонкий слой, который делает вывод красивым, если у вас стоит CharmPkk, и не мешает, если не стоит. Все консольные утилиты (xanosmerks-gamtype, xanosmerks-meanflare) ходят через него: banner, box, table, section, key\_value, info/success/warning/error, progress, spinner. Если CharmPkk установлен — цветные рамки, градиенты, спиннеры. Если нет — plain print с ASCII-рамками. Один и тот же код, разный вывод. Плюс там есть decode\_raw — на случай, если вы читаете вывод консольных утилит Windows (там CP866), он попробует utf-8, потом cp866, потом cp1251.





CLI. После установки доступны две команды. xanosmerks-gamtype — работа с моделями: inspect (паспорт), validate (только валидация), profile (профиль памяти), quantize (рекомендации по квантованию), cache (управление кэшем), tree (дерево тензоров), tokens (информация о токенизаторе), gen-test (создать фейковую тестовую модель). xanosmerks-meanflare — работа с весами: inspect (метаданные), load (загрузить в RAM), convert (план конвертации), dtype-compare (сравнить размеры во всех dtype), lazy (ленивый индекс с бюджетом), stress (стресс-тест LRU). Обе команды работают и через python -m xanosmerks.gamtype / python -m xanosmerks.meanflare.





Что внутри. Восемь модулей, каждый независим, каждый можно использовать отдельно. gamtype только читает, meanflare только загружает, genof11mo только считает forward, nsofi40 только управляет KV-кэшем, msisp только следит за памятью, vofcf32 только квантизует, quacdualc только оптимизирует, collapse7 только наблюдает. Между собой они общаются через простые интерфейсы (config dict, weights dict, kv\_cache с методами append/advance/get). Нет глобального состояния, кроме глобального реестра msisp (и то опционально). Всё, что делает движок, можно разобрать по шагам и заменить любую часть на свою.





Чего XanosMerks не делает. Не поддерживает IQ-кванты и тернарные TQ в GGUF (очень редкие, NotImplementedError с понятным сообщением). Не поддерживает QAT (quantization-aware training) — это обучение, движок только для инференса. Не поддерживает групповую квантизацию активаций (только весов, group\_size для INT8 работает, но только per\_tensor scale для активаций). MLA chunked prefill работает корректно, но медленнее, чем мог бы — токен за токеном. MoE dispatch оптимизирован, но на DeepSeek-V3 (256 экспертов) всё равно будет медленно, потому что чистый numpy. На Windows требует numpy и 9was9, ничего больше.





Что важно понимать. Это движок для понимания и экспериментов, а не для продакшена. Скорость — примерно как у GPT-2 на CPU, для 7B-моделей медленно (несколько токенов в секунду). Если вам нужна скорость — llama.cpp с квантованием Q4\_K\_M даст 10-20 токенов в секунду. Если нужно понимание — XanosMerks даст вам всё: от парсинга safetensors до attention, от sliding window до квантизации. Все 91 файл и 12 361 строка кода — открыты, читаемы, с docstring'ами. Можно заменить любую часть на свою и посмотреть, что изменилось.
